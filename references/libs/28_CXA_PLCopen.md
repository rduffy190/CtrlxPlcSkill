# 28 CXA_PLCopen

## 28.1 Introduction and overview

The PLC library CXA_PLCopen provides functions to control axes and kine‐
matics. The function blocks orient at the PLCopen standard.
The library divides the functions into two groups:
● Single axes
  Function blocks for single-axis control

● Axis groups
  Function blocks to control kinematics

## 28.2 Time response of the function blocks

Time response of the function blocks complies with the PLCopen standard.
Triggering function blocks are provided with an “Execute" input and with the
outputs “Done", "Active", "Error", "ErrorID" and "ErrorIdent". The processing
starts at a rising edge at the "Execute” input. During processing, the “Active”
output is set. If an error occurs during processing, the "Error" output is set.
All other Boolean outputs are reset. After the processing, the output is set
to “Done”. After setting, the outputs “Error” and “Done” remain active for at
least one cycle. They remain active when the “Execute” is set.
Monitoring function blocks are provided with an “Enable" input and with the
outputs "InOperation", "Active", "Error", "ErrorID" and "ErrorIdent". The proc‐
essing starts at a rising edge at the “Enable” input. The “Active” output is set
while preparing new values.

## 28.3 Malfunction

The function blocks issue the error code of the secondary functions if pos‐
sible. Own error codes are defined in some cases.
If an error is present, the “Errors” of the respective function block is set. The
system error code can be composed as follows using ErrorIdent.Additional1
and ErrorIdent.Additional2:
● Main diagnostics: ErrorIdent.Additional1
● Detailed diagnostics: ErrorIdent.Additional2
The main diagnostics includes the library code. The detailed diagnostics
includes the error code in the library.
The error code can be generated by the PLCopen library (main diagnostics
is 16#0A0F0103), other PLC libraries (e.g. main diagnostics is 16#090Fxxxx,
which indicates that the error is being transmitted by CXA_Motion) or other
apps.
For the expected error codes, refer to ⮫ Chapter 28.12.1 CXA_PLCopen - Error
codes on page 908.

disabled with MB_ResetFixedStop.
During the motion, the PLCopen state of the axis is set to "DIS‐

If the commanded target position is reached, the function block is set to the
"DONE" state and the PLCopen state of the respective axis is set to "STAND‐

If an error occurs before the function block is executed (e.g. violation of

executed.

the command is queued and waiting to be executed.
If the function block is in the "Active" state and the "InBuffer" output is inac‐
tive, the command controls the axis.
If the function block is in the "Active" state, no new command may be exe‐
cuted.

● Asynchronous motion: All axes start at the same time, but their motion is
  not synchronized.
● Dynamic boundaries: Each axis reaches its target position as quickly as
  possible, subject to its individual dynamic limits, as modified by the speci‐
  fied factors.
● State: The kinematics is in the "MOVING” state while moving.
● If the traversing motion is aborted by another traversing command, the
  "CommandAborted" output is set.

● The kinematics has to be enabled before the MB_MoveDirectAsync function
  block can be used.
● The kinematics may not be in the “ERRORSTOP” state.
Function block execution sequence:
● Initiation: The function block is enabled at a rising edge at the “Execute”
   input.
● Indicator when active: The "Active" output is set. Please note that this does
   not mean the move is executed immediately, but rather that a move is
   pending or that the "Execute" input remains set to TRUE.
● Completion: As soon as all axes have reached their target positions, the
   "Done" output is set, and the kinematics goes to the "STANDBY" state.
Troubleshooting:
● Preprocessing errors: If an error occurs before processing—for example, if
  motion limits are exceeded—the "Error" flag is set.
● Errors during the motion: If an error occurs during the motion, the "Error"
  output is set, and the kinematics also goes to the "ERRORSTOP" state.

Functional description
The function block MC_MoveLinearAbsolute traverses the kinematics to a cer‐
tain position. The kinematics has to be enabled before using the MC_Group‐
Enable function block. Furthermore, the Kinematic must not be in the
"ERRORSTOP" state.
The function block is enabled at a rising edge at the “Execute” input. The
"Active" output is set. However, this does not mean that a motion is already
executed. The "Active" output remains set as long as a motion s still pending
or the "Execute" input is TRUE.
The kinematics is in the "MOVING” state while moving. The “Done” output is
set after reaching the target position. The kinematics enters the "STANDBY"
mode. If an error occurs before processing, e.g. as motion limits were
exceeded, the "Error" output is set. If the error occurs during the motion, the
kinematics is additionally set to the "ERRORSTOP" state.
If the traversing motion is canceled by another traversing command, the
“CommandAborted” output is set.
If the axis is still traversing when the function block is enabled, it is traversed
as follows depending on the “BufferMode” input:
● mcAborting:
  The currently executed traversing motion is canceled and the new com‐
  mand is executed immediately.
● mcBuffered:
  The command is in the queue and executed if all previously commanded
  traversing motions are completed and the axis is in standstill. The
  “InBuffer” output is set during the waiting time.
The blending motion is specified in the “TransitionParameter” input. It
describes the transition between two subsequent motion commands.
● TransitionParameter[0]:
  Distance between the end position of the first motion command (E1) and
  the beginning of the blending motion (E1‘).
● TransitionParameter[1]:
  Distance after the starting position of the second motion command (S2)
  and the return to the original path (S2‘).

The "pathSmooth" mode is specified in the "TransitionParameter" input
parameter. It describes the transition between several consecutive motion
commands. The value [0,1] of "TransitionParameter" is reserved for the
blending mode.
● TransitionParameter[2] :
   Eps: Maximum permissible tolerance for eps.
● TransitionParameter[3]:
   RoundingType: Rounding method used to enable a command option for the
   transition of motion commands, e.g., (The "PolyTrans" command option).
● TransitionParameter[4]:
   PreparedCmds: Number of subsequent commands to be fully prepared.
   BauchSet this value to 0 to use the variant without overhead.

PathSmooth mode can only be enabled if: BufferMode = mcBlending and
TransitionMode = TMPathSmooth

Disable "pathSmooth" in the following cases:
1. "NonBuffer" or "buffer" command

2. TransitionMode is TMNone or TMBlending

Uses the "UpdatePathSmooth" property to update EPS files when "pathS‐
mooth" is enabled.

## 28.10 PhaseLimitSwitch

### 28.10.1 Introduction and overview

        The function block MB_DigitalCamSwitch implements a freely programmable
        limit switch with any number of switches on a switch track. The basic prin‐
        ciple of the programmable limit switch is that discrete outputs are switched
        on or off based on the position of a master axis (linear and rotary). The
        programmable limit switch supports with or without OVS module. If an over‐
        sampling module is connected, a correspondingly higher resolution of the
        programmable limit switch signals can be achieved.

Functional description
The MB_DigitalCamSwitch function block extends (EXTENDS) the IL_EnableI‐
nOpBase function block so that the "Enable" input and the "InOperation",
"Error", "ErrorID" and "ErrorIdent" outputs inherit from IL_EnableInOpBase.
"OversamplingFactor"
"OversamplingFactor" shows how often the output can change its state within
one cycle time. After implementing the function block, an output pattern with
the corresponding number of bits is generated in "Output". The number of
bits depends on the "OversamplingFactor" input.
"OversamplingFactor" can assume any value between 1 and 1000. The default
value of "OversamplingFactor" is 1.
If I/O components do not use an oversampling module, set the "Oversampling‐
Factor" input to the default value.
When connecting an oversampling module, set the value of the "Oversampling‐
Factor" input equal to the setting values of the oversampling module, as the
function block does not check whether the connected hardware is an over‐
sampling module.
Relation of "OversamplingFactor" and size of "Outputs"
"Outputs" should be big enough to include all bits. The data type of "Outputs"
is a byte array. Thus, the number of bytes of "Outputs" should be greater than
(OversamplingFactor + 7)/8.

Example:
If an "OversamplingFactor" of 30 is selected for example, it corresponds to a
bit pattern of 30 bits that have to be written after "Outputs".
It should be greater than:
TO_UINT ((30+7)/8) = 4

"Hysteresis"
This parameter prevents the output from switching too often if the axis is
at the switching point and the current position varies around the switching
point. The value set at the "Hysteresis" input is applied to all switches. If a
negative value is entered, it is automatically applied as positive value.
The hysteresis is only applied when the direction changes. In forward as well
as in backward direction, the hysteresis has to be run through first before the
master axis position is applied.
The following illustration shows two programmable limit switches, each
between 100° and 150°.

The center curve shows the switch output without hysteresis, the lower curve
shows the switch output with a hysteresis of 20°. The upper curve represents
the position.
The master axis first moves in positive direction via the beginning of the
switches and then in negative direction. The switch with and the switch
without hysteresis switch on at 100°. At 110°, the axis changes its direction
and moves now in negative direction. The switch without hysteresis switches
off again at 100°. In contrast, the switch with hysteresis switches off at 90°.
This is caused, as for the switch with hysteresis, the hysteresis has to be
crossed after a change in direction before the master position is applied
again. In the example, the direction is changed at 110° and the hysteresis
is 20°. Thus, the master axis position is only applied again at 110° - 20° = 90°.
At 90°, the switch is switched off. Thus, the output is deleted.
"MasterPhaseOffset"
"MasterPhaseOffset" is used to add a value to the axis position determined
via the "Axis" input. The result of the addition is used for a modulo operation.
For a modulo-scaled axis of 360°, a "MasterPhaseOffset" of 450° causes an
effective offset of only 90° (450° modulo 360° is 90°). Offsets higher than one
modulo value are thus not possible.
The effect of the "MasterPhaseOffset" is like an offset of all switches. Positive
"MasterPhaseOffset" values can switch switches earlier, negative values can
switch switches later. Thus, all switches can easily be moved simultaneously.
The input is processed cyclically. Thus, it allows a dynamic adjustment.
"Force/ForceValue"

These two inputs can be used to directly check the output. If the "Force" input
is set to FALSE, the output is determined by the programmable limit switch.
The "ForceValue" input is not significant.
If the "Force" input is set to TRUE, the state of the output is determined by
the "ForceValue". Thus, the output can be set irrespective of the state of the
programmable limit switch useful for maintenance purposes for example. The
output is fixedly set to TRUE or FALSE. Bit patterns are not possible. This can
be used for maintenance purposes for example.
"Outputs"
Depending on the oversampling factor, the output data array transferred at
the "Outputs" input can be of variable size. This is labeled by "*" in the
declaration (ARRAY [*] OF BYTE). As user, you are only responsible to create
an array in defined size that is subsequently transferred to the function block.
A possible declaration of the "Outputs" output data array is shown for dif‐
ferent oversampling factors in the following.

"Switches"
The size of the "Switches" input is dynamic and determined when creating the
program. Thus, the exact number of switches required can be created. The
contents of the structure are cyclically analyzed upon each function block call.
This allows to dynamically change the elements of the switches at runtime.
To reach the lowest computation times possible, do not create more switches
than required!
If single switches are temporarily not required, they can be disabled using the
structural element "Active".
Each switch has a starting and an end position. This allows to specify a "First‐
OnPosition" and a "LastOnPosition" (or time) for each switch. In addition to
a mechanical switch, the switch can be enabled for a certain duration and a
common lead time and dwell time can be defined for each switch.
If FirstOnPosition > LastOnPosition, the switch acts inversely and is only
switched off within these positions.
"TrackOptions"
A switch track is an element describing the characteristics of the program‐
mable limit switch related to an output capable of oversampling. The
MB_TRACK_REF structure contains elements to set the behavior for a switch
track. Unlike for "Switches", this function block can only edit one output/
switch track. Thus, there is no array of MB_TRACK_REF as input, but only the
structure.
"On/OffCompensation" is specified in nanoseconds. It can be positive or neg‐
ative. Positive means that the output switches after reaching the switching
position, negative means that the output switches before reaching the
switching position.
"On/OffCompenTimeDef" shows whether the "On/OffCompensation" has a
positive or negative signal.
If "OnCompenTimeDef" is set to TIME_DEFINITION.Positive, a positive signal is
defined for OnCompensation.

If "OffCompenTimeDef" is set to TIME_DEFINITION.Positive, a positive signal
is defined for OffCompensation.
Area/modulo computations
Using the "Axis" input, the function block can access the current axis position
and axis velocity required for the computations.
The PLS can be used for rotary as well as for linear axes. Position data can
be computed in modulo format as well as in absolute format (axis running
forward and backward).
In both cases, the programmable limit switch units are based on the units
defined for the axis.

Implementation details

"OnCompensation"/"OffCompensation"
PLCopen defines the "On/OffCompensation" only for motions in positive
direction. In this case, the "OnCompensation" relates to the "FirstOnPosition"
while the "OffCompensation" relates to the "LastOnPosition".
How can this be defined for motions in negative direction?
Based on applications for which the lead times are used to compensate for
the on and off delays with actuators, this means that the "OnCompensation"
is responsible for the rising edge of the signal, the "OffCompensation" for the
falling edge of the signal.
If it is traveled in positive direction, the "OnCompensation" relates to the
"FirstOnPosition" and if it is traveled in negative direction, the "OnCompen‐
sation" relates to the "LastOnPosition". The "OffCompensation" is defined
accordingly.

the "FirstOnPosition" and "LastOnPosition"?

It has been decided to wait for a rising edge of the switch output. When the

  set the "OversamplingFactor" input to 1. In this case, there are no oversam‐
  pling benefits.
● If an output module (XI90202) with oversampling function is connected,
  oversampling factors from 1 to 1000 are supported.
● As the function block of the hardware is not known, no extensive tests
  can be carried out. When selecting the "OversamplingFactor", ensure that it
  matches the settings in the I/O device. Otherwise, there will be a malfunc‐
  tion that cannot be diagnosed in the function block.

Runtimes of the programmable limit switch function blocks
The runtime of the function block does not depend on the "Oversampling‐
Factor". As one instance of the function block only represents one switch
track, the runtime depends only on the number of switches. To achieve
the lowest possible computation times, do not create more switches than
required.
The following equation can be used to approximately compute the required
runtime for MB_DigitalCamSwitch:
Runtime in μs: (Number of switches) * 1.8 + 15
The specification is only used for a rough estimate of time for a specific
configuration. If exact times are required, perform own measurements. The
"pMaxRunTime" property of the MB_DigitalCamSwitch function block can read

out the maximum runtime of the function block.
