# 6.4 Troubleshooting

### 6.4.1 Error detection and error reaction

    Basic principles of error reaction
This chapter describes the error detection and error reaction in ctrlX MOTION
to ensure safe and reliable operation.
ctrlX MOTION follows the basic principle: "If an error is detected, consequen‐
tial damage to people, machines and products have to be avoided by initiating
a suitable error reaction."
The following guidelines are followed:
Local error reaction:
1.      The error reaction is only triggered in the affected parts of the system.
        This enables the user application to carry out specific error reactions in
        other parts of the system.
Light error reaction:
2.   The error reaction is as gentle as possible (instead of maximum
     dynamics) so as not to further endanger the machine or the process.
Depending on the type of error, the Motion App
1.   F0 errors "non-fatal errors"
2.   F2 error "Error single axis/kinematics"
3.   F6 error "Error all axes/kinematics"
are generated in the Motion app.

The F2 errors are again divided into the error classes
● LIGHT: Errors in which the axis can still follow the command value input
● SEVERE: Errors in which the axis no longer follows the specified values
● CRITICAL: critical error, e.g. error when trying to access the memory
subdivided.
This subdivision determines the error reaction of the Motion kernel within the
Motion app.

Error reaction in a distributed system
In a distributed system, as occurs in ctrlX AUTOMATION, the error reaction is
typically as follows:
1. Error detection:
1.   A component (e.g. a drive) detects an error.
2. Error message:
2.   The occurrence of the error is reported to other relevant components
     (e.g. ctrlX MOTION).
3. Error reaction:
3.   Each component carries out its corresponding error reactions on the
     basis of the error message.
4. Error diagnostics:
4.   The diagnostic function indicates which component reported the error.
5. Error analysis:
5.   The source of the error can be diagnosed using a suitable tool (e.g. ctrlX
     DRIVE Engineering or DRIVE Connect app for ctrlX DRIVE).
There are also comparable sequences if the error occurred in another compo‐
nent. If the error is generated directly by ctrlX MOTION, details of the cause of
the error can be found in the messages in the diagnostic log.

Error types and associated error reactions
Error handling is composed of the ctrlX CORE diagnostic system (see doc‐
umentation "ctrlX OS, chapter 11 ctrlX Diagnostic system" ⮫ Link to web
documentation) as well as specific error handling within the Motion App.
The error types are divided into different categories, each of which triggers
different error reactions.

                           configuration errors)       other error reactions

                                                       is stopped

                                                       all axes/kinematics. Typ‐

Axis/kinematic error in detail
A distinction is made between two escalation levels for axis and kinematic
errors:
● LIGHT error: A gentle error reaction is initiated
● SEVERE error: A hard error reaction is initiated

LIGHT error
The aim of a LIGHT error is to bring the affected axis/kinematics to a standstill
as gently as possible:
● Setting the axis/kinematics to standstill with the currently commanded
  dynamic
● Setting to standstill on the commanded track
● The power of the axis is not switched off
● The command has to support this error reaction (e.g. does not apply to
  the SyncMotion command or the Torque command). The description of the
  commands indicates if the command does not support a soft error reaction
                      Please note that in the event of a LIGHT error in many
        CAUTION       commands, the current commanded dynamics is used

                      for deceleration. This can lead to significantly longer
                      stopping distances than if the configured dynamics was
                      used.

SEVERE error
A SEVERE error triggers a special ESTOP command that brings the axis/kine‐
matics to a standstill as quickly as possible:
● Grouping of the kinematics is canceled (each axis decelerates separately)
● The commanded path is left
● Setting the axes to standstill:
  – The error reactions and the stopping of the individual axes can be con‐
      figured. See also Adaptation error reaction SEVERE error
  – If necessary, axis limit values can also be slightly exceeded in order
      to avoid damaging the axis limit switches. The acceleration can be
      exceeded by up to 20 %, the jerk by up to 100 %
● Switching off the power after reaching standstill
● If a drive command is active, it is canceled

    Error causes
Errors can have various causes:
● Incorrect or inconsistent configuration:
  – Missing licenses, invalid values in the configuration, axis configuration
     does not match the drive configuration
  – Check when switching from SETUP to OPERATION
  – F0 error as diagnostics
  – If critical (missing licenses, basic configuration inconsistent, subsequent
     errors likely): Switching is canceled ® back to SETUP
  – If only parts are affected (non-critical faults): Mark as invalid ® if invalid
     configuration is used in command ® Command error
● Command error:
  – Inconsistent command parameters, invalid configuration referenced,
     incorrect status of the axis/kinematics
  – F2 error as diagnostics
  – Error reaction: affected axis/kinematics is stopped
     If supported by the active command: ⮫ LIGHT error on page 319
     If not supported by the active command: ⮫ SEVERE error on page 319
● Monitoring (e.g. axis limit switch):
  – F2 error as diagnostics
  – ⮫ SEVERE error on page 319

 ● Drive error or field bus error:
   – F2 error as diagnostics
   – ⮫ SEVERE error on page 319
 ● Error generated by the application:
   – Error generation with the "ML_SetErrorLevel" command (see ⮫ Chapter
      7.7 General commands on page 735
   – F2 error as diagnostics
   – By command (PLC, Data Layer, script, Celix)
   – Choice between ⮫ LIGHT error on page 319 and ⮫ SEVERE error
      on page 319

Forwarding errors
If the axis in which an error occurs is part of a gantry link or a kinematic
system, errors are forwarded as follows:
 ● Gantry system: Error is copied to another gantry axis
 ● Grouped kinematics: Error is copied to the kinematics
 If a ⮫ SEVERE error on page 319 occurs in one kinematic system, the error is
 copied to all grouped axes of the kinematic system.

Interaction with other components
Axis and kinematic errors can also be caused by other system components.
The axes or kinematics commanded by the component are assigned a
⮫ SEVERE error on page 319. This error reaction is triggered as follows:
 ● PLC is switched to STOP
 ● Aborting a G-Code or Python script

Configurable error reaction of specific functions
The error reaction can be configured for certain functions (e.g. monitoring),
e.g:
 ● A synchronously coupled slave axis cannot follow the master axis. Refer to
    ⮫ Chapter Error reaction on page 126
 ● The actuator does not follow the command value input of the control.
    Refer to ⮫ Chapter 6.4.2 Drive does not follow the command values of the
    control on page 321
 ● Gantry link error. Refer to ⮫ Chapter Error classification and reaction princi‐
    ples on page 161
 Please note the information on special features of the error reaction in the
 description of the functions used in your application.

After the error reaction
Once the error reaction has been completed, all affected axes are stopped.
They are therefore in a safe state. Before these axes can be commanded again,
all pending errors have to be reset. This also resets internal states.
The following reset commands are available:
 ● ⮫ Chapter 7.2.3 AxsReset - AxsReset - Resetting the axis on page 335
 ● ⮫ Chapter 7.3.18 KinReset - Resetting the kinematics on page 590
 For gantry axes, reset the master axis first. This dissolves the gantry link. All
 gantry slave axes can then be reset.

### 6.4.2 Drive does not follow the command values of the control

Overview
To prevent mechanical damage or impermissible axis behavior, the Motion
system constantly monitors whether the real drives are following the com‐
mand value input of the control. If a drive does not or no longer follows the
command values of the axis, the Motion system distinguishes between the
following cases:
● The Motion system executes a function that expects a drive to be allowed
  to temporarily ignore command value input from the control (e.g. for drive-
  controlled referencing, positive stop drive procedure). There is no error
  reaction
● The Motion system expects drives to follow the command value input of

  the control and sets the relevant axes to the error state as an error reaction
● The Motion system expects drives to follow the command value input of
  the control, but due to the configuration by the user, there is no error
  reaction or only a diagnostic message (e.g. for a feeder)

Configurable error reactions via Data Layer
The user can configure the following error reactions via the Data Layer node
".../motion/axs/<axs_name>/cfg/dev-err-reaction/dev-not-following":
● NONE
  The Motion command is continued. There is no error reaction. If traces
  are activated for the "motion/core" trace unit, a trace message of type
  MESSAGE is triggered (code 090A0FFF)
● MESSAGE
  The Motion command is continued. A diagnostic message of type MES‐
  SAGE is triggered as an error reaction (code 090A0030 + 0C57010F)
● WARNING
  The Motion command is continued. A WARNING type diagnostic message is
  triggered as an error reaction (code 090E0030 + 0C57010F)
● SEVERE_ERROR
  As an error reaction, the Motion command is canceled, the axis is set to
  the ERRORSTOP state by setting a SEVERE_ERROR and a corresponding
  diagnostic message is triggered (code 090F2002 + 0C57010F). This is the
  default error reaction

Special features and exceptions
The error reactions for certain commands are already preset.

● Power command
  If the drive follows the command value input of the control when the
  power is switched on with the "Power" axis command (and no other error
  occurs), the status of the command is set to DONE. Otherwise, the com‐
  mand remains in the IN_WORK state until the drive follows again.
  If the drive no longer follows the axis command values after the power has
  been successfully switched on, an error reaction is not triggered again until
  the first Motion command for the axis has been issued
● Gantry command
  When a gantry slave axis command is executed, a cyclical check is executed
  to verify whether the drives of the master axis and slave axis are complying
  with the command value input of the control. If a drive no longer follows,
  the gantry motion is aborted and error reactions are triggered for the
  master and slave axis:
  The axis causing the error is set to the ERRORSTOP state by setting a
  SEVERE_ERROR and a corresponding diagnostic message is triggered (code
  090F2008 + 0C550156, 0C550157, 0C550159 or 0C55015A).
  The SEVERE_ERROR is copied to the other axis, which is then also set
  to the ERRORSTOP state. A corresponding diagnostic message is also trig‐
  gered for this axis

Configuration via the user interface
The dialog for specifying the error reaction in the event that the real drive
does not follow the command value input of the control can be found in
the Motion axis configuration when editing the axis properties under the
advanced settings.

Configuration example via REST
Method: PUT
https://<ip-addr>/automation/api/v2/nodes/motion/axs/<axs_name>/cfg/dev-
err-reaction/dev-not-following
Payload:
{
    "errReaction":"SEVERE_ERROR"
}

Temporarily disable the "Drive follows controller command values" monitoring
function using a command
Using the "AxsSetDriveFollowsMonitoring" command (see ⮫ Chapter 7.2.44
AxsSetDriveFollowsMonitoring - Turning "Drive follows command values" mon‐
itoring on or off on page 516 ), you can temporarily disable and then re-
enable the configured error reaction for the "Drive follows command values"
signal.
Use case:
● Disabling the configured monitoring. Call "AxsSetDriveFollowsmonitoring"
   with the option "false"
● Selecting the drive's internal operation mode, e.g., "Brake test," "drive-
   guided homing," etc.
● Exiting the drive's internal operation mode
● Enabling the configured monitoring: Call "AxsSetDriveFollowsMonitoring"
   with the option "true"
After an axis reset or after switching from the "Configuration" state to the
"Operation" state, the configured monitoring is reactivated.

The command is also available for PLCs (CXA Motion Library, ML_AxsSetDrive‐
FollowsMonitoring()), Python, and the bundle interface.

### 6.4.3 Extended diagnostic options

Overview
To facilitate insight into the actively running system, there are two options to
obtain debug information:
● Trace
● Real-time data

Trace
Traces are mainly useful for debugging an application (PLC, Python, REST)

to obtain sequential information about what is happening within the Motion
system.
The following debug information is available by a trace output:
State changes
● PLCopen state changes of the motion objects and the Motion system
● The outputs contain the current cycle
Commands
● Parameters and type of the new command, including interface from which
   it has been issued
● Command state in command buffer such as PREPARED, ACTIVE, DONE
● Interrupting events, such as e.g. buffered commands, abort or interrupt
   commands
Startup
● Sequential start-up steps as well as successful completion of start-up
Loading/Saving
● Load/save operations for e.g. restoring of a saved configuration
Error information
● Additional information about errors not part of the official diagnostic pro‐
   tocol output
Enabling the trace
Traces have to explicitly enabled via the bundle API of common.log.trace
which is part of the app.automationcore:
Method: PUT
URL: /trace/rexroth-automationcore/units/motion/core
Payload:
To activate the trace messages and further information, see ⮫ ctrlX
AUTOMATION How-tos - "How to generate a system report and switch on
additional traces"

{"type":"bool8","value":true}

Real-time data
Real-time data (RT) facilitates access to data in the Motion system. This data
is also available upon non-real-time (NRT) Data Layer requests, such as inter‐
polated values, state changes of a Motion object.

Example non-real-time addresses
● https://<ip-addr>/automation/api/v2/nodes/motion/axs/<axs_name>/
  state/values/ipo/pos
● https://<ip-addr>/automation/api/v2/nodes/motion/axs/<axs_name>/
  state/opstate/plcopen

The real-time data access provides the option to use this data for additional
use cases, e.g.:
● Oscilloscope functionality
● Debug information
● Real-time applications
Basics
Each Motion object is equipped with an individual real-time memory area
which can be configured by the user via the NRT Data Layer. To avoid a power
overhead, this function is disabled by default and only becomes active if the
user has configured it via the NRT Data Layer.
Read real-time data available for configuration
Three different object types facilitate access to real-time data. The provided
data can be accessed via the following NRT addresses of the Data Layer:
● https://<ip-addr>/automation/api/v2/nodes/motion/axs/<axs_name>/state/
   realtime/available-data
   Lists available real-time data for axis objects
● https://<ip-addr>/automation/api/v2/nodes/motion/kin/<kin_name>/state/
   realtime/available-data
   Lists available real-time data for kinematic objects
● motion/state/realtime/available-data
   Lists available real-time data for the global Motion system
The available real-time data is similar to the already available NRT nodes
(sub address) which are already registered in the Motion system (see access
example via REST). However, not all NRT nodes can be accessed via RT. Via
this node, the user can access a list of all supported RT data.

Access example via REST
Method: GET
URL:      https://<ip-addr>/automation/api/v2/nodes/motion/axs/<axs_name>/
state/realtime/available-data
Return values:

{
     "type": "arstring",
     "value": [
         "state/values/ipo/pos",
         "state/values/ipo/vel",
         "state/values/ipo/acc",
         "state/values/act-cmd/pos",
         "state/err-level",
         "state/opstate/plcopen",
         ...
     ]
}

Writing of an active real-time data configuration

The configuration can be written individually for each object via the following
NRT address of the Data Layer:
● https://<ip-addr>/automation/api/v2/nodes/motion/axs/<axs_name>/cfg/
   realtime/active-data
   Writing of the active real-time data configuration to the specified axis
   object.
● https://<ip-addr>/automation/api/v2/nodes/motion/kin/<kin_name>/cfg/
   realtime/active-data
   Writing of the active real-time data configuration to the specified kinematic
   object.
● motion/state/cfg/active-data
   Writing of the active real-time data configuration to the global Motion

   system.
Additional information
As soon as a valid configuration is written (in NRT context), the configuration
becomes active immediately and the real-time data are provided in each cycle
(e.g. 2 ms).
● The configuration process cannot be used in real-time (NRT nodes) so that
  the configuration can take some time (miliseconds)
● During the configuration process, the currently configured real-time
  memory is reconfigured. Thus, no access to the real-time data of this object
  is possible!
● A configuration can be overwritten at any time
● To stop the real-time data for an object, an empty configuration (empty
  array of strings) has to be written

Configuration example via REST
Method: PUT
https://<ip-addr>/automation/api/v2/nodes/motion/axs/<axs_name>/cfg/real‐
time/active-data
Payload:

{
"type":"arstring","value":
    [
        "state/values/ipo/pos",
        "state/values/ipo/vel"
    ]
}
